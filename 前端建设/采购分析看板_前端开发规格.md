## 0. 结论摘要（先看这一节）

### 0.1 邮件 POC 是什么

| 项 | 内容 |
|---|---|
| 数据源 | GDMS `auditpayment` 付款审计报表（5 个 txt，对应 5 个 server） |
| 期间 | Document Date 2025-07-01 ~ 2026-06-30（FY2526），2026-07-06 提取 |
| 覆盖 | **仅 5 家香港公司**：BMHK / BMMA / NEVB / SVHK / SVMA；SDIB、SDMA 不含（未用 GDMS） |
| 粒度 | **付款笔数**（payment-based），46,910 笔 |
| 币种 | HKD，合计 593.80M |
| 分类层级 | **供应商级**（vendor-level），由采购手工在 Jupyter 里打标 |
| 产出 | 6 个全局筛选器 + 6 个 KPI + 5 个图表 |

### 0.2 当前库是什么（关键差异）

| 项 | 当前 `procurement.db` |
|---|---|
| 数据源 | KUBE 的 **PRPO 采购申请 + PO 采购订单**（45K + 48K 行） |
| 期间 | 2024-07 ~ 2026-10（28 个月） |
| 覆盖 | **62 家大陆公司**、14 个品牌 |
| 粒度 | **单据级**（transaction-level），44,987 张已完成的 PRPO |
| 币种 | CNY，合计 15.95 亿 |
| 分类层级 | **交易级**（PRPO 上直接带 采购类别 / 子类别 / 支出类型 / 供应商属性） |

**核心结论：这不是同一份数据。** 邮件 POC 是"香港、按付款、按供应商打标"；当前库是"大陆、按单据、按交易打标"。

因此：

- **可以直接照搬**：6 个筛选器骨架、5 个图表形态与视觉、4 个 KPI 定义
- **必须重定义**：`Server`（库里没有 server 概念）、`Procurement Spend / Non-Procurement Spend`（库里不存在"非采购"记录）
- **不能照搬**：任何 POC 的绝对数值（HKD 593.8M / 46,910 笔），口径不同，比了没意义

### 0.3 三个必须提前拍板的问题

| # | 问题 | 文档建议 |
|---|---|---|
| 1 | `Procurement Spend` vs `Non-Procurement Spend` 二分不成立 | 改成 `已分类 / 未分类` 双卡，把数据缺口显性化（§4.2 Option B，推荐） |
| 2 | `Server` 筛选器（5 个）在库里对应什么 | 改为 **品牌 Brand（14）+ 公司（61）** 两级筛选（§3.6） |
| 3 | 金额列是带 `¥` 和千分位的 **字符串** | 必须清洗，否则 `SUM()` 恒为 0（§7.1） |

## 1. 数据源与口径对照

### 1.1 字段对应总览

| POC 概念 | POC 字段 | 当前库落点 | 可用性 |
|---|---|---|---|
| 事实粒度 | 一行 = 一笔付款 | 一行 = 一张 PRPO | ⚠ 口径不同 |
| 金额 | `Spend` | `fct_prpo."含增值税总价"` | ✅ 需清洗 |
| 时间 | `MonthStart` | `fct_prpo.提交日期` / `审批时间` | ✅ |
| 供应商 ID | `SupplierId` | `fct_prpo."供应商 AVL 编号"`（如 `CP005454`） | ✅ 97.9% 可回 `fct_supplier` |
| 供应商名 | `SupplierName` | `fct_prpo.供应商名称` | ✅ |
| 一级类别 | `PurchaseCategory` | `dim_category.CategoryName`（经 `采购类别` 关联） | ✅ 100% |
| 二级类别 | `PurchaseCategory_HKMT` | `dim_subcategory.SubCategoryName`（经 `Table - 采购子类别`） | ✅ 99.88% |
| 支出类型 | `ExpenditureAccount` | `dim_expense_type.ExpenseTypeEn`（经 `支出类型`） | ✅ 100% |
| 供应商类型 | `VendorExemptionCategory` | `dim_supplier_attribute.SupplierCateEn`（经 `供应商属性` 前 1 位） | ⚠ 24% 为空 |
| 公司/Server | `Server_Raw` | `dim_company.CompanyAbbreviation` / `.Brand` | ⚠ 语义需重定义 |
| 采购标记 | `ProcurementSpendFlag` | 无，需派生 | ⚠ 见 §4.2 |
| PO 标记 | `PO_flag` | `fct_prpo.采购订单号` 非空 | ✅ 99.74% |

### 1.2 为什么"金额"口径不同（前端必须知道）

| | POC | 当前库 |
|---|---|---|
| 含义 | 实际付出去的钱（cash out） | 申请/下单的承诺金额（commitment） |
| 时点 | 付款日 | 提交日 / 审批日 |
| 与 PO 关系 | 大量付款无 PO（PO Spend 仅 30.1%） | 绝大多数有 PO（99.8%） |

→ **POC 的 `PO Spend % 30.1%` 在当前库会变成 99.8%**，不是 bug，是数据源决定了库里只收走完流程的申请。

### 1.3 口径切换选项（供决策，不是前端实现）

| 方案 | 金额 | 优点 | 缺点 |
|---|---|---|---|
| **A. 申请口径（推荐 v1）** | `fct_prpo."含增值税总价"` | 与分类字段同源，44,987 行全可用 | 与 POC 数字不可比 |
| B. 订单口径 | `fct_po."总采购订单总额（人民币)"` | 更接近承诺金额 | 分类字段要回 PRPO 取，多一次关联 |
| C. 实付口径 | `fct_po."总支付总额（人民币）"` | 最接近 POC | **只有 33,193/48,007 有值（69%）且无支付日期**，做月度趋势会断 |

## 2. 数据底座：`vw_dash_base`

前端不要直接 JOIN 7 张表，统一走一个视图。**以下 DDL 已在库上验证，JOIN 命中率见 §2.3。**

### 2.1 视图定义

```sql
DROP VIEW IF EXISTS vw_dash_base;
CREATE VIEW vw_dash_base AS
SELECT
    p.表单编号                                        AS doc_id,
    substr(p.提交日期, 1, 7) || '-01'                 AS month_start,      -- MonthStart
    p.提交日期                                        AS submitted_at,
    p.审批时间                                        AS approved_at,
    p.公司                                            AS company,
    c.CompanyAbbreviation                             AS company_short,
    c.Brand                                           AS brand,            -- 替代 Server（品牌层）
    p.部门                                            AS department,
    p.采购类别                                        AS category_raw,
    cat.CategoryName                                  AS category,         -- 一级类别
    p."Table - 采购子类别"                             AS subcategory_raw,
    sub.SubCategoryName                               AS subcategory,      -- 二级类别
    p.支出类型                                        AS expenditure_raw,
    et.ExpenseTypeEn                                  AS expenditure,      -- A&P / CAPEX / OPEX / TRADE
    CASE
      WHEN p.供应商属性 LIKE 'A%' THEN 'A-Fully Exempt'
      WHEN p.供应商属性 LIKE 'B%' THEN 'B-Partially Exempt'
      WHEN p.供应商属性 LIKE 'C%' THEN 'C-Not Exempt'
      ELSE 'Unknown'
    END                                               AS vendor_type,
    CASE
      WHEN p.采购类别 IS NOT NULL AND TRIM(p.采购类别) <> ''
       AND p."Table - 采购子类别" IS NOT NULL AND TRIM(p."Table - 采购子类别") <> ''
       AND p.支出类型 IS NOT NULL AND TRIM(p.支出类型) <> ''
       AND (p.供应商属性 LIKE 'A%' OR p.供应商属性 LIKE 'B%' OR p.供应商属性 LIKE 'C%')
      THEN 'Y'
      ELSE 'N'
    END                                               AS classified,       -- 分类完整度标记
    CASE
      WHEN p.采购订单号 IS NOT NULL AND TRIM(p.采购订单号) <> '' THEN 'Y' ELSE 'N'
    END                                               AS po_flag,          -- PO_flag
    p."供应商 AVL 编号"                                AS supplier_id,      -- SupplierId
    p.供应商名称                                       AS supplier_name,    -- SupplierName
    p.选择采购方法                                     AS method,
    CAST(REPLACE(REPLACE(REPLACE(COALESCE(p."含增值税总价", '0'),
         '¥',''), ',',''), ' ','') AS REAL)           AS spend             -- Spend（清洗后）
FROM fct_prpo p
LEFT JOIN dim_company      c   ON p.公司                = c.Company
LEFT JOIN dim_category     cat ON p.采购类别             = cat.Category
LEFT JOIN dim_subcategory  sub ON p."Table - 采购子类别" = sub.SubCategory
LEFT JOIN dim_expense_type et  ON p.支出类型             = et.ExpenseType;
```

### 2.2 为什么用 `fct_prpo` 而不是 `fct_po`

- `fct_prpo` 44,987 行**全部为"已完成"状态**，提交日期、审批时间、类别、子类别、支出类型、供应商属性都在同一张表上，一次 JOIN 拿全。
- `fct_po` 48,007 行**没有**类别/子类别/支出类型，要用 `已批准的采购申请参考 → fct_prpo.表单编号` 再关联一次；且含 107 条"草案"无提交日期。
- 若采用方案 B（订单口径），底座改为 `fct_po` LEFT JOIN `fct_prpo`，其余字段映射不变。

### 2.3 JOIN 命中率（实测）

| 关联 | 命中 | 命中率 |
|---|---|---|
| 公司 → `dim_company.Company` | 44,987 / 44,987 | **100.00%** |
| 采购类别 → `dim_category.Category` | 44,987 / 44,987 | **100.00%** |
| 子类别 → `dim_subcategory.SubCategory` | 44,934 / 44,987 | 99.88% |
| 支出类型 → `dim_expense_type.ExpenseType` | 44,987 / 44,987 | **100.00%** |
| 供应商 AVL 编号 非空 | 44,925 / 44,987 | 99.86% |
| 金额可解析 > 0 | 44,983 / 44,987 | 99.99% |

> 供应商 ID 回 `fct_supplier`：3,227 个 distinct 中 3,159 个能命中 `Vendor Code`（97.9%）。若要展示 AVL 到期日/状态，用 LEFT JOIN，缺失不许丢行。

### 3.4 为什么要改 `Server`

POC 的 5 个 server（BMHK/BMMA/NEVB/SVHK/SVMA）是 **GDMS 系统实例 / 法人实体**，一个 server 对应一批店。当前库里：

- 没有 server 字段
- 直接对应物是 `dim_company.CompanyAbbreviation`（61 个公司简称，如 `深圳宝悦`）
- 61 个值做筛选可以，但做**堆叠图的系列**太多（61 种颜色无法区分）

→ **筛选器用「品牌」（14）+ 可选「公司」（61，带搜索）**；堆叠图系列固定用品牌。

### 3.5 `Sub-Category` 与 `Category` 的级联

`dim_subcategory` 里子类别名自带编号前缀（`1-`、`2-`…），但没有 `Category` 外键。若要做级联，需按前缀规则或人工建立映射表（当前库暂无此关系）。

**v1 建议**：不做级联，`Sub-Category` 用可搜索多选；`Update Dashboard` 后若与已选 Category 无交集，直接提示"当前组合无数据"，不要静默返回空图。

## 4. KPI（6 个）

### 4.1 定义与 SQL

```sql
-- 通用：把筛选条件拼进 WHERE，例如
--   AND (:brands 为空 OR brand IN (...))
--   AND (:categories 为空 OR category IN (...))
SELECT
  SUM(spend)                                                    AS total_spend,
  SUM(CASE WHEN classified='Y' THEN spend ELSE 0 END)           AS classified_spend,
  SUM(CASE WHEN classified='N' THEN spend ELSE 0 END)           AS unclassified_spend,
  COUNT(*)                                                      AS transactions,
  SUM(CASE WHEN po_flag='Y' THEN spend ELSE 0 END)              AS po_spend,
  COUNT(DISTINCT supplier_id)                                   AS suppliers
FROM vw_dash_base
WHERE month_start BETWEEN :from_month AND :to_month;
```

### 4.2 `Procurement / Non-Procurement` 二分的处理（重要）

**事实**：`fct_prpo` 44,987 行全部来自 KUBE 的采购申请，`采购类别` 100% 有值 → 按 POC 原定义（类别为空 = 非采购），`Non-Procurement Spend` 恒等于 **0**。

三种处理，二选一：

| 方案 | KPI 组合 | 说明 |
|---|---|---|
| **Option B（推荐）** | Total / **Classified** / **Unclassified** / Transactions / PO Spend % / Suppliers | 把"未分类 24%"变成可见指标，符合库现状，且能驱动数据治理 |
| Option A | Total / Procurement / Non-Procurement / Transactions / PO Spend % / Suppliers | 保留 POC 原样，但 Non-Procurement 显示 `0` 或 `N/A`，必须加脚注"当前数据源不含非采购支出" |

> 不建议为了凑数字把 `TRADE` 或某个类别硬掰成 Non-Procurement——那是编数据。

## 5. 图表（5 个）

### 5.1 Chart 1 — Monthly Spend by Server（堆叠柱）

| 项 | POC 字段 | 库字段 |
|---|---|---|
| X 轴 | `MonthStart` | `month_start` |
| Y 轴 | `Spend` | `SUM(spend)` |
| 堆叠/颜色 | `Server_Raw` | **`brand`**（14 个） |
| Tooltip 1 | Spend | `SUM(spend)` |
| Tooltip 2 | SupplierId (distinct) | `COUNT(DISTINCT supplier_id)` |
| Tooltip 3 | Transaction Count | `COUNT(*)` |

```sql
SELECT month_start, brand, SUM(spend) spend,
       COUNT(DISTINCT supplier_id) suppliers, COUNT(*) tx
FROM vw_dash_base
WHERE month_start BETWEEN :from_month AND :to_month AND brand IS NOT NULL
GROUP BY month_start, brand
ORDER BY month_start, spend DESC;
```

- **必须补全缺失月份为 0**，否则 X 轴会跳月（用 `LEFT JOIN` 月份序列，或前端补齐）。
- 系列顺序建议按期间总额降序，`BMW&MINI` 永远第一（占 78%）。
- 若切到"公司"维度（61 个），只画 **Top 8 + 其他**，否则颜色不可辨。

### 5.2 Chart 2 — Category Spend Pareto（帕累托）

| 项 | 字段 |
|---|---|
| 类别轴 | `category` |
| 柱值 | `SUM(spend)`，按金额**降序** |
| 累计线 | 累计额 / 总额，右轴 0–100% |
| Tooltip | `COUNT(DISTINCT supplier_id)`、`COUNT(*)` |
| 参考线 | 80% 虚线（`#C00000`，dash 6 4） |

```sql
SELECT category, SUM(spend) spend, COUNT(DISTINCT supplier_id) suppliers, COUNT(*) tx
FROM vw_dash_base
WHERE month_start BETWEEN :from_month AND :to_month AND category IS NOT NULL
GROUP BY category
ORDER BY spend DESC;
```
累计百分比在前端算（`running_total / SUM(total)`），不要用窗口函数也行，但要注意浮点。

### 5.3 Chart 3 — Spend Distribution by Expenditure Type（环形）

| 项 | 字段 |

## 7. 数据坑位与清洗规则（**开发前必读**）

### 7.1 金额是字符串，`SUM()` 恒为 0

```sql
-- ✗ 错：类型声明是 REAL，但实际存的是 '¥30,000.00'
SELECT SUM("总采购订单总额（人民币)") FROM fct_po;   -- → 0.0
```

`typeof()` 实测：`fct_po` 四个金额列全是 `text`（48,005 行）、`fct_prpo."含增值税总价"` 全 `text`（44,986 行）。

```sql
-- ✓ 对：去 ¥、去千分位逗号、去空格后转数值
CAST(REPLACE(REPLACE(REPLACE(x, '¥',''), ',',''), ' ','') AS REAL)
```

好在 **100% 可解析**（坏值 0），见 §2.3。

### 7.2 `采购类别` 有 96 种写法，必须走维度表归一

像 `Accessories and  parts-汽车附件精品及零配件`、`Accessories and parts-汽车附件精品及零配件`、`Accessoriesandparts-汽车附件精品及零配件`、`汽车附件精品及零配件-Accessories and  parts` 都是同一类别。

→ **绝不能直接 `GROUP BY 采购类别`**（会出现 96 个柱子）。必须 `JOIN dim_category ON 采购类别 = dim_category.Category` 拿 `CategoryName`（实测 100% 命中，归一到 11 个）。

### 7.3 `供应商属性` 有变体 + 空值 + 脏值

```
'C 常规供应商-完全豁免及部分豁免以外的供应商为常规供应商'  12,813
NULL                                                     10,877  ← 24.2%
'C常规供应商'                                              6,397
'B部分豁免'                                                3,066
'B 部分豁免-保险公司'                                       2,898
…
'0'                                                          41  ← 脏值
'010-89126870'                                                3  ← 脏值（电话串进字段）
```

→ 只取**首字符** `A/B/C` 归一到 3 类，其余一律 `Unknown`。**不要**用 LIKE 匹配全称。

### 7.4 `财政年度` 字段不可靠，不要用它筛期间

实测分布：`FY2425` 覆盖 2024-07~2026-10、`FY2526` 覆盖 2025-03~2026-10。字段值与实际提交日期不对应。

→ 期间筛选一律用 `substr(提交日期,1,7)` 或 `审批时间`，不要用 `财政年度`。

### 7.5 其他

| 坑 | 处理 |
|---|---|
| `fct_po` 107 行「草案」提交日期为空 | 用 PRPO 作底座时不受影响 |
| `fct_prpo."Table - 采购子类别"` 有 53 行为空 | 归到 `Unknown`，筛选器里单列一项 |
| 公司名是 `英文全名-中文全名` 长串 | 展示一律用 `dim_company.CompanyAbbreviation`（61 个简称） |
| `供应商名称` 是 `中文-英文` 混排 | Top10 展示截断到 20 字 + tooltip 全文 |
| 币种 | 库里全是 CNY，**不要**沿用 POC 的 `HKD` 前缀 |
